# 把遊戲開發發包給 AI

這份文件回答一個問題：**這個專案要怎麼切，才能安全地交給 AI agent 做？**

結論先講：遊戲開發是**對 AI 最不友善的軟體類型之一**，但不是因為程式難，
而是因為它的驗收條件天生是主觀的、視覺的、動態的。
只要把「主觀」轉成「可量測」，AI 的產出品質會立刻從不可用變成可用。

---

## 1. 為什麼遊戲特別難發包

| 障礙 | 具體表現 |
|---|---|
| **看不到畫面** | AI 寫完 shader 不知道結果長怎樣，只能靠推理 |
| **驗收條件主觀** | 「這個後座力手感不對」無法寫成測試 |
| **時間維度** | 動畫時序、鏡頭阻尼、命中回饋，靜態截圖看不出來 |
| **跨檔案耦合** | 改一個渲染 pass 可能影響全部材質 |
| **沉默失敗** | 曝光錯 10 倍，程式不會報錯，只會全白 |

最後一項是最危險的。**這個專案開發過程中就真的發生了**：
`Sky` 把太陽圓盤（亮度 `vSunE * 19000` ≈ 7×10⁵）烘進 PMREM，
和 `DirectionalLight` 重複計算，整個畫面全白。沒有任何 console error。

## 2. 發包前的三個硬性前置條件

**這三項沒做完，不要發包。** 少了任何一項，AI 的產出你都無法驗收，
只能自己重看一遍——那還不如自己寫。

### 前置 1：可執行的視覺驗證

本專案已具備（`tools/`）：

```bash
npm run build     # 建置必須零錯誤
npm run shots     # headless Chromium 截圖 8 個固定視角 + console error 即失敗
npm run probe     # 參數掃描，輸出像素統計
```

關鍵掛鉤是 `main.js` 裡的兩行：

```js
globalThis.__GAME__ = this;              // 讓外部腳本能操控整個遊戲狀態
poseCamera({ position, yaw, pitch })     // 不需要 pointer lock 就能擺鏡頭
```

**任何 ticket 都不得移除這兩個掛鉤。** 它們是自動化驗收的唯一入口。

### 前置 2：凍結的模組邊界

見 `docs/SPEC.md` §3。依賴方向是單向的，模組之間互不 import。
這不是潔癖，是**讓兩個 agent 可以同時改兩個檔案而不衝突**的前提。

### 前置 3：把「好看」翻譯成數字

這是最重要、也最常被跳過的一步。

**反例（不要這樣發包）：**
> 「調整光照讓畫面更好看一點」

**正例：**
> 在 `goldenHour` 預設下，於 `tools/probe-exposure.mjs` 的 courtyard 視角，
> 調整 `exposure` / `envIntensity` / `hemiIntensity`，使得：
> - mean luma ∈ [0.32, 0.46]
> - p05 luma ≥ 0.015（暗部不得死黑）
> - p95 luma ∈ [0.78, 0.95]
> - clipped ratio < 3%
>
> 附上掃描表格與最終數值。

第二種寫法 AI 做得到，而且做得比人快——它可以掃 50 組參數再挑。
第一種寫法它只會亂猜。

> **這正是本專案曝光問題的解法。**
> 不是「把數字調小看看」，而是寫 `probe-exposure.mjs` 讀 `gl.readPixels()`
> 算 luma 分位數，掃參數空間，然後從候選裡挑。
> **AI 判斷不了「好看」，但可以把「好看」變成搜尋問題。**

## 3. Ticket 的解剖學

每張發包的 ticket 必須有這七欄。缺一欄就會出事。

```markdown
### T-XX  <一句話標題>

**目標**    做完之後畫面/行為有什麼可觀察的差異（一到三句）

**主要檔案** src/xxx/Yyy.js          ← 只列一到兩個
**可以改**   src/zzz/Www.js          ← 明確授權
**不要碰**   src/core/Renderer.js    ← 明確禁止，含理由

**驗收條件**
- [ ] `npm run build` 零錯誤
- [ ] `npm run shots` 零 console error
- [ ] draw call ≤ 250（附 shots 輸出）
- [ ] <此 ticket 專屬的可量測條件>

**參考**    規格章節 / 外部文件連結 / 既有的類似實作

**風險**    這個改動可能弄壞什麼
```

「**不要碰**」欄位比「可以改」更重要。
AI 最常見的失敗不是做不出來，是**順手重構了它不該碰的東西**。

## 4. 什麼該發包、什麼不該

| | 類型 | 為什麼 |
|---|---|---|
| ✅ | **有數學定義的**：shader pass、後處理、程序生成、噪聲函式 | 對錯有客觀答案 |
| ✅ | **有既定 API 的整合**：GLTF 載入、Web Audio、Gamepad API、localStorage | 文件即規格 |
| ✅ | **機械式轉換**：抽常數到 config、加 JSDoc、補測試、命名統一 | 純文字操作 |
| ✅ | **有 repro 的 bug** | 驗收條件自明 |
| ✅ | **有 profiler 數據的效能優化** | 前後數字可比 |
| 🟡 | **參數調校** | 讓 AI 掃參數並輸出統計表，**人做最後選擇** |
| 🟡 | **敵人 AI 行為** | 可發包，但要附「不得出現的行為」清單 |
| ❌ | **「讓它變好看」** | 無驗收條件，必然來回三輪還是不對 |
| ❌ | **關卡設計、手感調校** | 需要真的用手玩，AI 玩不了 |
| ❌ | **美術資產創作** | 用 CC0 資產庫，發包的是「整合」不是「創作」 |
| ❌ | **跨 5+ 檔案的架構重構** | 上下文超出可靠範圍，衝突機率高 |

最後一列值得展開：**不要叫 AI 生成美術資產**。
Poly Haven（HDRI／貼圖／模型）、ambientCG（PBR 材質）、Mixamo（綁定角色＋動作）、
Kenney（CC0 模型音效）已經涵蓋 90% 的原型需求，品質遠高於任何生成結果。
發包給 AI 的應該是「把這個 GLB 接進 `EnemyManager`，保留現有 hitbox 標記」。

## 5. 可直接複製的 prompt 模板

```
你要在 GTA5mini 這個 three.js FPS 原型上完成一張 ticket。

【先讀這些，不要跳過】
- docs/SPEC.md              模組邊界、pass 順序、效能預算。這是契約。
- docs/TASKS.md 的 T-XX     你這次要做的 ticket
- 你的 ticket 標示「主要檔案」的那一到兩個檔案

【硬性規則】
1. 只改 ticket 授權的檔案。要動別的，先停下來說明理由。
2. 不得新增任何 runtime 相依（three 以外）。
3. 不得發出任何外部網路請求；資產一律程序生成或內嵌 base64。
4. 不得移除 globalThis.__GAME__ 或 Game.poseCamera()。
5. 每幀更新路徑（step/update/render）中不得呼叫 new。
6. 不得更動 core/Renderer.js 的 pass 順序。

【完成前必須執行並貼出輸出】
   npm run build
   npm run shots
兩者都必須零錯誤。貼出 shots 印出的 scene stats。

【回報格式】
- 改了哪些檔案、每個檔案改了什麼（一行一個）
- 驗收條件逐項打勾，附證據
- 你不確定的地方（如果有）
- 你想改但沒有被授權的地方（如果有）

現在開始 T-XX。
```

## 6. 多 agent 編排

模組邊界是單向的，所以下列組合**可以安全並行**：

```
併行組 A（互不相干，可同時發三個 agent）
├── T-05  換 HDRI          → world/Environment.js
├── T-08  音效系統          → 新增 audio/，main.js 只加接線
└── T-13  手把支援          → core/Input.js

併行組 B（必須排在 A 之後）
├── T-07  Mixamo 角色      → entities/Enemies.js（依賴 T-05 的資產管線）
└── T-09  尋路             → entities/Enemies.js  ← 與 T-07 衝突，要串行
```

規則：**同一個檔案同時只能有一個 agent。**
Ticket 的「主要檔案」欄位就是排程用的鎖。

跑法建議：每個 agent 一個 git worktree，各自跑 `npm run shots`，
產出的截圖放進 PR 描述，人只做「看圖選一個」的決策。

## 7. 常見失敗模式

| 症狀 | 原因 | 對策 |
|---|---|---|
| 畫面全白／全黑 | 光照單位、tone mapping、雙重計光 | 用 `npm run probe` 量，不要用眼睛猜 |
| 「我加了效果但看不到」 | pass 順序錯，或 pass 沒 enable | 在 ticket 裡明確指定插入位置 |
| draw call 暴增 | 每個物件一個 material | 驗收條件加 draw call 上限 |
| 幀率掉但沒人發現 | 沒有效能驗收條件 | `shots` 已輸出統計，寫進驗收 |
| AI 順手重構了無關檔案 | 沒有「不要碰」欄位 | 每張 ticket 都寫 |
| 三輪還是不對 | 驗收條件是主觀的 | 這張 ticket 本來就不該發包 |
| 資產載入失敗 | AI 加了外部 CDN 連結 | 規則 3，並在 shots 檢查 console |

## 8. 成本現實

以本專案的規模與 ticket 顆粒度估算：

| Ticket 類型 | 一輪成功率 | 備註 |
|---|---|---|
| 機械式轉換（抽常數、補文件） | 高 | 幾乎不會錯 |
| 有數學定義的（shader、程序生成） | 中高 | 錯了通常是單位／色彩空間 |
| API 整合（GLTF、Web Audio） | 中高 | 錯了通常是生命週期／dispose |
| 參數調校（附掃描腳本） | 中高 | 沒有掃描腳本則極低 |
| 主觀品質 | 低 | 不要發包 |

真正省時間的地方不是「AI 寫得比較快」，而是**AI 可以平行掃參數空間**——
`probe-exposure.mjs` 那 15 組組合，人手動試要半小時，腳本跑一次兩分鐘。

**把人的時間留給「選哪一個」，把機器的時間花在「產生候選」。**
